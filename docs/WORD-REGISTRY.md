# Word Registry — one place for every Benga word's links

The website shows ~900 different Benga words. Each word can have:

- a **recording** (an `.mp3` on Cloudinary), and
- an **entry in the Living Dictionary** (an id like `9b0fb8a4-e76e-…`).

Before, every page typed these by hand (with typos: 81 audio ids didn't match their word).
Now there is **one file** that connects each word to its links, and the pages only say *which word* to show.

## How it works

```
 Page shows "Enâ"
       │
       ▼
 src/utils/audioId.js  ── the rule ──►  key "en_a_"          (never typed by hand)
       │
       ▼
 src/data/lexicon/word-registry.json
   "en_a_": {
     "word": "Enâ",
     "livingDictionaryId": "9b0fb8a4-…",  ──► 🔗 link to the exact dictionary entry
     "audio": "recorded",                 ──► ▶  play  <Cloudinary>/en_a_.mp3
     "audioFile": null,                        (only if the file has a different name)
     "notes": ""
   }
```

| Field | What to put | If empty |
|---|---|---|
| `word` | The spelling used as a label in the admin page | — |
| `livingDictionaryId` | The id at the end of the entry URL: `…/benga/entry/<id>` | The link opens the dictionary **search** for the word |
| `audio` | `missing` or `recorded` | `missing`: a muted icon is shown, no play button |
| `audioFile` | Cloudinary file name without `.mp3`, **only** if it isn't the key | The key is used as file name |
| `notes` | Anything useful for humans | — |

The code that reads the registry is `src/services/wordLinks.js` (used by `BengaWord.vue`).

## The key rule (in one line)

Lower-case the word, turn each accented letter into `_letter_`, join several words with `-`:
`Whâki → wh_a_ki`, `Mūēngi → m_u_e_ngi`, `Ekâi ebe → ek_a_i-ebe`.
Different accent marks on the same letter give the same key (`Hāngā` and `Hângâ` → `h_a_ng_a_`), so
spellings from other sources still match. Tests: `npm test`.

## Everyday tasks

### 1. Edit words in the browser (easiest)

```bash
npm run serve
```

Open <http://localhost:8080/admin/palabras> (the port is shown in the terminal).
This page exists **only on your computer**: it isn't part of the published website.

- Search a word, or filter: *Sin enlace al diccionario*, *Audio pendiente*, *No usadas*…
- **Living Dictionary:** click *Buscar*, open the right entry, copy its URL from the browser and
  paste it in the box. The page keeps only the id.
- **Audio:** after uploading `<key>.mp3` to Cloudinary, set *grabado* and click *▶ probar*.
- Click **Guardar cambios**. The file `src/data/lexicon/word-registry.json` is updated.
  Check the change in VS Code's *Source Control* panel, then commit.

### 2. Fill many words at once from a spreadsheet

Make a CSV (Excel: *Save as → CSV UTF-8*) whose first row names the columns:

```csv
word,livingDictionaryId,audio
Enâ,9b0fb8a4-e76e-4d83-bf79-32a6dd3f23cc,recorded
Eko,7d2851f2-f884-476c-b784-055170e6773c,
```

```bash
npm run words:import -- path/to/list.csv
```

- An empty cell changes nothing.
- A word that isn't on any page yet is added, so you can prepare ids before writing the content.
- The admin page's **Exportar CSV** button produces a file in this same format. You can export,
  edit in Excel, and import again.
- Or give Claude the list and ask it to "import it into the word registry". Keep the CSV in
  `scripts/imports/` as a record (example: `living-dictionary-2026-11-11.csv`).

### 3. After adding or changing content on a page

```bash
npm run words:sync
```

It finds every Benga word on the site, **adds new words** to the registry (existing entries and
your edits are never changed) and prints a report:

| Report section | What to do |
|---|---|
| NEW words added | Nothing; fill their links when you can |
| Entries not used on any page | Usually a word that was renamed; delete the old entry or keep it |
| Different spellings that share one key | The same word is written two ways (e.g. `Itánde` / `itânde`); pick one |
| Orthography warnings | A letter that Benga doesn't use, or a Spanish accent (`á`→`â`) |
| Hand-typed audio ids that differ | Old ids still written in page data. The site ignores them now; they're removed in roadmap Phase 2, but some reveal a content doubt (see REVIEW-LOG) |

`npm run words:check` prints the same report without changing files. It fails if words are
missing, which is useful for automatic checks later (roadmap 9.2).

### 4. Correct a word's spelling

Correct it **on the page or data file** where it appears, then run `npm run words:sync`.
The corrected spelling gets its own key. The old entry is then listed as "not used on any page":
copy its dictionary id or audio state to the new entry and delete the old one.

## Files

| File | Who edits it |
|---|---|
| `src/data/lexicon/word-registry.json` | You (admin page, CSV import or by hand) |
| `src/data/lexicon/word-usage.json` | Generated by `words:sync`, never edit. Spellings and files per key |
| `src/utils/audioId.js` | The key rule (code) |
| `src/services/wordLinks.js` | Connects the registry to the link rules (code) |
| `src/utils/linkRules.js` | How audio and dictionary URLs are built (code, tested) |
| `scripts/words-sync.mjs`, `scripts/words-import.mjs`, `scripts/lib/*` | The npm commands (code) |
| `scripts/imports/*.csv` | Lists you imported, kept as a record |

## Why a JSON file and not a database (yet)

- ~900 words today, a few thousand later: one JSON file handles that easily, and the site stays
  free to host with no server.
- Git keeps every change, so mistakes are easy to undo and you can see who changed what.
- Keys are stable, so moving to a real database later (roadmap Phase 10, e.g. when the community
  uploads recordings) is a direct copy: one row per key, the same fields as columns.
